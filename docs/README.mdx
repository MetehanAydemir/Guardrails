## Product Documentation

Product documentation for the toolkit is available at
[https://docs.nvidia.com/nemo/guardrails](https://docs.nvidia.com/nemo/guardrails).

## Building the Documentation

1. Make sure Node.js 22 is installed.

1. Install Python 3.10 through 3.13 and [uv](https://docs.astral.sh/uv/getting-started/installation/)
   for OpenAPI generation. The first generation run installs the locked Python dependencies.

1. Install the documentation dependencies:

   ```console
   npm ci
   ```

1. Build the documentation:

   ```console
   make docs-fern
   ```

   The Fern docs configuration is validated with the pinned Fern CLI.

## Updating the API Reference

`fern/openapi.yml` is generated from the stable FastAPI server routes and Pydantic
models. After changing a public server contract, install the locked development
dependencies and regenerate the specification:

```bash
uv sync --locked --group dev
uv run --locked python scripts/export_openapi.py
```

Commit the regenerated file with the source change. The generator imports the
application without starting its lifespan or calling model providers. It disables
the optional chat UI so installed extras do not change the exported contract.

`make docs-fern`, `make docs-fern-live`, and both publish targets regenerate the
OpenAPI specification and Python SDK reference through
`make docs-fern-generate-references`. You can also run that target directly.

Keep API reference summaries, examples, and streaming or error documentation in
`fern/openapi-overlay.yml`. Fern applies this overlay to the generated specification
through `fern/generators.yml`. Change request and response model fields in Python
instead of overriding them in the overlay.

Before handing off a change, check that the generated file is current and validate
the documentation:

```bash
uv run --locked python scripts/export_openapi.py --check
make docs-fern
```

The `OpenAPI freshness` workflow runs the same read-only freshness check on pull
requests and `develop` pushes affecting the contract or its generation inputs. A
stale or missing file fails the check and prints the regeneration command.

The documentation conformance workflow initializes the generated baseline without
comparing it to the legacy handwritten schema only when the base revision has no
exporter and the runtime sources and dependency files are unchanged. Subsequent
changes retain the existing breaking-change comparison.

`npm run test:docs-scripts` also compiles the API reference with Fern and checks
existing endpoint identities and curated examples against the pre-generation
baseline in `scripts/tests/fixtures/openapi-reference.json`. Update that baseline
only when an intentional documentation change modifies those public examples or
endpoint identities.

## Live Documentation Server

For local development with automatic rebuilding on file changes, use one of the following methods:

### Option 1: Local Fern Server

```bash
make docs-fern-live
```

The Fern development server starts locally and updates as you edit docs files.

### Option 2: Published Branch Preview

```bash
make docs-fern-preview-watch
```

This watches local docs and Fern configuration changes and publishes a preview for the current Git branch.

### Option 3: Direct Fern Command

```bash
cd fern
npx --yes fern-api@$(node -p "require('./fern.config.json').version") docs dev
```

Once the server is running:

- Open the local URL printed by Fern
- Edit documentation files or Fern configuration
- Save the file
- The browser will automatically refresh with the updated content

Press `Ctrl+C` to stop the server.

## Publishing the Documentation

Both `make docs-fern-publish-staging` and `make docs-fern-publish-public` regenerate
the OpenAPI specification and Python SDK reference before publishing. If either
generation step fails, publishing stops. The GitHub Actions staging job and PR
preview job use the same preparation target. OpenAPI generation runs without Fern
publishing credentials; the existing freshness CI check still requires you to
commit schema updates with the source change.

Tag the commit to publish with `docs-v<semver>`.
Push the tag to GitHub.

To avoid publishing the documentation as the latest, ensure the commit has `/not-latest` on a single line, tag that commit, and push to GitHub.

### Publishing a Version from a Git Ref

Historical versions are declared in `fern/docs.yml` with a Git `ref` that points to an immutable tag. When you publish, Fern builds the version's pages, navigation, assets, and API references from that ref while applying the current theme and version selector. See [Build a version from a Git ref](https://buildwithfern.com/learn/docs/configuration/versions#build-a-version-from-a-git-ref) in the Fern documentation.

The repository uses two tag types for documentation:

| Tag pattern | Purpose | Retention |
| --- | --- | --- |
| `docs-v<semver>` | Triggers the documentation publishing workflow. | Follow the existing publishing process. |
| `fern-docs-snapshot-v<semver>[-r<number>]` | Keeps a curated historical source commit reachable for a Fern version. | Permanent and immutable. |

Pushing a snapshot tag makes the source commit available to Fern and CI, but does not publish the documentation. Only tags matching `docs-v*` trigger the tag-based documentation publishing workflow.

The referenced commit must contain the `fern/` directory at the same repository path. Add the version after you identify the frozen snapshot:

```yaml
versions:
  - display-name: Latest
    path: ../docs/index.yml
    slug: latest
  - display-name: v0.24.1
    ref: fern-docs-snapshot-v0.24.1
    slug: v0.24.1
  - display-name: v0.24.0
    ref: fern-docs-snapshot-v0.24.0
    slug: v0.24.0
  - display-name: v0.23.0
    ref: fern-docs-snapshot-v0.23.0-r2
    slug: v0.23.0
  - display-name: v0.22.0
    ref: fern-docs-snapshot-v0.22.0
    slug: v0.22.0
```

Use the existing release tag directly when it contains the exact documentation snapshot and required Fern configuration. When the historical source needs a documentation-only correction or compatibility update, create a curated snapshot commit and tag it with `fern-docs-snapshot-v<semver>`. Do not use a bare commit SHA that is reachable only from a pull request or temporary branch. The commit can become unavailable after a squash merge and branch deletion. Avoid release branches for frozen versions because republishing from a branch can change historical content.

#### Creating a Curated Snapshot

Prepare the snapshot from the release tag in a temporary branch and worktree. For example:

```bash
VERSION=v0.24.0
SNAPSHOT_BRANCH=docs/${VERSION}-fern-snapshot
SNAPSHOT_WORKTREE=../Guardrails-${VERSION}-fern-snapshot
SNAPSHOT_TAG=fern-docs-snapshot-${VERSION}

git worktree add -b "$SNAPSHOT_BRANCH" "$SNAPSHOT_WORKTREE" "$VERSION"
```

In the snapshot worktree:

1. Make only the changes required to render that historical version.
1. Do not commit generated SDK reference pages. The documentation build generates and caches those pages from the snapshot source.
1. Run pre-commit on the changed files.
1. Create a DCO-signed snapshot commit.

After you commit the snapshot, create an annotated tag from the main worktree:

```bash
SNAPSHOT_COMMIT=$(git -C "$SNAPSHOT_WORKTREE" rev-parse HEAD)
git tag -a "$SNAPSHOT_TAG" "$SNAPSHOT_COMMIT" -m "Fern docs snapshot for ${VERSION}"
```

Add or update the version entry in `fern/docs.yml` so its `ref` matches `SNAPSHOT_TAG`. Run `make docs-fern`, then use `make docs-fern-preview-watch` to inspect the ref-backed version in a published preview. Confirm its navigation, links, assets, and generated SDK reference.

Push the snapshot tag before you push the branch update that references it. Otherwise, remote CI cannot resolve the ref.

```bash
git push origin "refs/tags/${SNAPSHOT_TAG}"
git ls-remote --tags origin "refs/tags/${SNAPSHOT_TAG}" "refs/tags/${SNAPSHOT_TAG}^{}"
```

For an annotated tag, the verification output includes the tag object and a `^{}` entry for the commit it references. After you verify the remote tag, follow the normal pull request workflow for the `fern/docs.yml` change.

The permanent tag, not the temporary branch, keeps the snapshot commit reachable. The snapshot commit does not need to be part of `develop`. It remains available after the feature pull request is squash-merged and its branches are deleted.

#### Revising a Published Snapshot Tag

Do not move, overwrite, or delete a snapshot tag. If you find a correction after pushing `fern-docs-snapshot-v<semver>`, create a new commit and use `fern-docs-snapshot-v<semver>-r2`. Continue with `-r3`, `-r4`, and so on for later corrections, and update `fern/docs.yml` to the new tag.

Keep the snapshot on a temporary branch until it passes review and validation so that the initial permanent tag usually represents the final content. The revision suffix is only for corrections discovered after a snapshot tag has been pushed.

The local Fern development server renders only versions backed by a working-tree `path`; use a published Fern preview to verify a `ref`-backed version.
